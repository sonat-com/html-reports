How to Write Release Notes People Actually Read

You shipped the update. The work is done, the tests pass, and the team is already planning the next sprint. Then someone asks: “What do we tell customers?”

That’s where release notes come in. Good release notes help customers find new features, warn them before something breaks, and cut down the “what changed?” tickets your support team would otherwise answer one by one. Bad ones get skipped, or worse, cause confusion.

This guide covers what release notes are, what to put in them, a structure you can reuse, and a free release notes template you can copy today.

What are release notes?

Release notes are a short, dated summary of what changed in a product release and how those changes affect the people who use it. They cover new features, improvements, bug fixes, and anything users need to act on, such as a feature being retired.

The key words are how those changes affect the people who use it. Release notes are not a record of what your team did. They are a message to your users about what’s different for them.

Release notes vs. changelog: what’s the difference?

The two terms get used interchangeably, but they usually serve different readers.

  • A changelog is a complete, chronological list of notable changes for every version. It is often technical and kept alongside the product itself. A well-kept changelog is still written for humans: it groups similar changes, puts the newest version first, and shows the release date for each one.
  • Release notes are curated for customers. They pick out what matters, explain the benefit in plain language, and point readers to help content when they need more.

One rule applies to both: never paste a raw list of code commits. Commit messages are full of internal shorthand and noise. A single user-facing change might span dozens of commits, and a dozen commits might add up to nothing a customer would notice.

If your product has both technical and non-technical users, keep both: a full changelog for people who want every detail, and release notes for everyone else.

What to include in release notes

Most release notes need the same core parts. Here’s what each one does.

A clear, dated title

Customers often relate more easily to a date than to a version number. A title like “November 2026 update” or “What’s new — 23 November 2026” tells readers at once whether they’ve seen it before. Add the version number too if your users rely on it.

When you write dates in full or in ISO format (2026-11-23), readers in different countries can’t misread the day and month.

A short summary up top

Start with two or three sentences for the reader who has ten seconds. What’s the headline change? Is there anything they must do? Put the details further down.

New features

Lead with new things. For each feature, say what it does for the user and where to find it. Keep it short, and link to the full how-to guide instead of repeating every step.

Improvements

Changes to existing features: faster loading, a clearer layout, a renamed setting. Describe what feels different to the user, not what you refactored behind the scenes.

Bug fixes

List fixes users would notice. Describe the fix from the user’s side: “Exported PDFs now keep your table formatting” is better than “Fixed table rendering bug in PDF export module.”

Breaking changes, deprecations, and removals

This is the section readers can least afford to miss. If a change means users must do something, or something they rely on will stop working, say so clearly and early. Tell them exactly what to do and by when. If you only get one section right, make it this one.

How to write release notes: 7 best practices

1. Write for your users, not your team

Picture explaining the update to a customer, not to a colleague. Drop internal project names, ticket numbers, and team jargon. If a term only makes sense inside your company, it doesn’t belong in release notes.

2. Start each item with the user’s outcome

The UK Government Digital Service’s guidance on release notes puts it simply: for each change, start by telling users directly how it affects them. Phrases like “You can now…” and “You no longer need to…” do this naturally.

Compare:

  • ❌ “Implemented bulk export functionality.”
  • ✅ “You can now export several topics at once from the topic list.”

3. Use active voice and address the reader directly

“You can now filter by date” is clearer than “Date filtering has been added.” Active voice also makes it obvious who does what, which matters most when the reader has to take action.

4. Keep it brief and link out for details

Release notes are not a user manual. Give a high-level summary of each change and where to find it. Then link to a step-by-step guide or video for anyone who needs more. If that guide doesn’t exist yet, that’s a signal to write it.

5. Make it scannable

Use headings, short bullets, and white space. Avoid walls of text and deeply nested lists — one level of sub-bullets is plenty. Only use a table when the content truly has rows and columns.

6. Use version numbers that signal impact

If you number releases, a widely used convention is MAJOR.MINOR.PATCH. You raise the major number for changes that aren’t backward compatible, the minor number for new functionality that is, and the patch number for backward-compatible bug fixes. Readers can see at a glance whether an update needs their attention.

7. Be consistent, every release

Use the same structure, the same section order, and the same naming for features as your product interface. Consistency teaches readers where to look. Publish notes for every release, too. Users who learn to trust your release notes will treat them as the source of truth for what changed.

Release notes template

Copy this release notes format and adapt it to your product. Delete any section that’s empty for a given release.

[Product name] — [Month Year] update (version X.Y.Z)
Released: [YYYY-MM-DD]

Summary
[2–3 sentences: the headline change and anything users must do.]

⚠️ Action required
- [What is changing or being removed] — [what users must do] by [date].

New features
- You can now [outcome]. Find it in [location]. [Link to guide]

Improvements
- [Feature] now [what's better for the user].

Bug fixes
- [What now works correctly, described from the user's side].

Coming soon / deprecations
- [Feature] will be retired on [date]. Use [replacement] instead. [Link to guide]

Release notes example

Here’s how the template looks filled in for a fictional project-tracking app:

Example App — November 2026 update (version 4.2.0)
Released: 2026-11-23

Summary: You can now share boards with people outside your team, and search is faster. If you use the old CSV import, switch to the new importer before 31 January 2027.

Action required

  • The legacy CSV import will be removed on 31 January 2027. Use Import → Spreadsheet instead.

New features

  • You can now share a board with guests by email. Open a board and select Share.

Improvements

  • Search results now load as you type.

Bug fixes

  • Due dates now display correctly in your local time zone.

Notice what’s missing: no ticket numbers, no “various bug fixes and performance improvements,” no internal team names. Every line tells the reader something about their own experience.

Where to publish your release notes

Release notes work best where users already look for help. That means alongside your product documentation, not buried in an email that gets archived. Many teams keep a single “What’s new” page with the newest release at the top, then link to it from inside the product and from their update emails.

A few things make that page much easier to maintain:

  • Version history. You can see and restore earlier versions of a page if something is published by mistake.
  • A review step. A second person checks breaking-change wording before it goes live.
  • Translation. If your customers read other languages, a release note in their language is far more likely to be acted on.
  • Search. Users searching your docs for a feature should find the release note that introduced it.

Conclusion

Great release notes are short, dated, consistent, and written entirely from the user’s point of view. Lead with what’s new, flag anything that needs action, describe fixes the way users experience them, and link to deeper guides instead of cramming them in.

Start with the template above for your next release. Within a few updates, your customers will know where to look and what to expect — and your support team will hear “what changed?” a lot less often.
