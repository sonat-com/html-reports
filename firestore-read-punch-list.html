Application reads are about 10% of the Firestore bill

Earlier estimates in this document scaled per-collection shares against the full billed read volume. That was wrong by roughly 8×. Two independent sources — this audit capture and the firestore.googleapis.com/document/read_count metric — agree that application traffic is ~200–490k reads/day. Billing says ~2.0M. Caching every collection in the platform saves about $7/month. Do this work for latency and blast radius, not for the invoice.

Unbounded query Webapp ~half day

Notification settings fetch every subscription a user has, unpaginated

Docer.DAL/Repositories/Notification/SubscriptionRepository.cs:23 — GetByUserId()

A bare WhereEqualTo("UserId", …) with no limit and no pagination, reached from GET /User/Subscriptions (UserController.cs:530) via NotificationBusiness.GetSubscriptions. One account already has just under 2,100 subscriptions, so each load of their notification settings reads all of them.

  Subscriptions       3.6   (peak 1,995 in a single call)
  Links               10.7

Fix

  • Paginate, or fetch only the subscription relevant to the entity being rendered.
  • GetByUserIdAndEntity() already exists two methods down and is the bounded form.

Why it matters

  • Cost is trivial. The problem is it scales with one user's subscription count and has no ceiling.
  • Worst read amplification in the system by an order of magnitude.
03
Latency Editor-Frontend / Webapp ~1d

The Reference Links count tiles are the slowest thing in the database

features/reference-links-dashboard/index.tsx:116 — three separate count() calls per load

All 9,437 aggregation queries on Monday were count() against Links. They are 3% of calls and the worst latency in the system by a wide margin — 5× the median of an ordinary query and 13× at p95. 

Mon Aug 24 — latency by method
                        calls     p50      p95      p99    total
  RunAggregationQuery   9,437   16.0ms  204.3ms  246.5ms    430s
  RunQuery            120,934    6.3ms   16.2ms   65.2ms  1,039s
  BatchGetDocuments   151,473    2.6ms    8.7ms   13.6ms    509s

The code comment above these calls reads "Firestore's count aggregation is cheap and React Query dedupes on the same key." The dedupe works; the premise about cost does not. Three sequential 200ms calls put roughly half a second of latency in front of the dashboard before a row is drawn.

Fix

  • Collapse Total / Broken / Ignored into one pass, or denormalise the counters onto the document.
  • Document.NumberOfBrokenLinks already exists — the pattern is established.

Note

  • The filters are narrow (SourceTopicId, SourceDocumentId + IsValid), so this is latency, not billed reads.

Read amplification Webapp 1–3d

77% of weekday reads are the same read repeated

Simulated TTL cache replayed over 272,431 Monday reads

Nearly half of it disappears with request-scoped memoisation alone — no shared cache, no invalidation, no staleness risk, just not fetching the same thing twice inside one request.

The heaviest individual repeats on Monday: Contents by TopicVersionId 15,585×, Items by PublishUrl 14,790×, Accounts by Slug 14,336×, DocumentVersions by Id 12,392×, Users by FirebaseUserId 10,172×, and one single Documents record 9,077×.

Start here

  • Request-scoped memoisation across the board — 47% for a fraction of the effort of a real cache.
  • Then a TTL cache on Accounts and Users, which reach 91% and 95%.

Not worth caching

  • Redirects — 14% hit rate. Nearly every lookup is a unique miss. Only negative caching helps, and only against scanners.
05
Cost Cloud-Functions ~half day

The daily backup is the largest identifiable line on the Firestore bill

Scheduler job firebase-schedule-firestoreBackup-us-central1 → ExportDocuments, 07:00 UTC daily

A full unfiltered export of every collection, every day. Firestore bills one read per document exported, so this is ~30M reads/month — roughly $18, against ~$9/month for all application traffic combined. 

export operation metadata, verified
  progressDocuments.completedWork   987,996
  progressBytes.completedWork       3,664,316,586   (3.66 GB)
  collectionIds                     (none — full database)
  runtime                           ~2m 45s
  backup bucket total               306 GiB

Options

  • Firestore managed backup schedules bill backup storage rather than read ops — likely cheaper and less code than the export-to-GCS function.
  • Or reduce cadence, or filter collectionIds to what a restore actually needs.

Check first

  • 306 GiB of retained backups with no visible lifecycle policy — worth confirming that GCS retention is intentional.
06
Read amplification Content-Processor ~1d

Link reconciliation reads ten documents per call and runs constantly

2,300 calls → 26,354 reads on Monday — 8.4% of the day's application reads

Links where SourceTopicId == … AND … pulls every existing link for a topic so the processor can diff against freshly extracted ones. That is a reasonable design, but it is the second-heaviest per-call read in the system and it re-runs on every content save.

It also caches extremely well — 92% at a 60-second TTL, 96% at five minutes — which suggests the same topic is being reprocessed repeatedly in short windows. Worth understanding why before optimising the query itself.

07
Unexplained GCP investigate

Two fifths of the read bill has no identified source

Sun Aug 23 — billed 2,000,686 · explained 1,192,019 · gap 808,667

Application reads and the daily export together account for 60% of billed reads. The remaining ~810k/day is unaccounted for. I would rather flag this than invent a cause for it.

Ruled out

  • Point-in-time recovery — disabled.
  • Managed backup schedules — none configured.
  • A second database — only (default) exists.
  • A second export job — one scheduler job, one daily operation.
  • count() aggregations — filters are narrow, so ~1 read each.
  • Incomplete capture — the Firestore metric independently corroborates the app figure within 10%.

Next step

  • Open a GCP support case with these three numbers; the SKU breakdown they can see is finer than the billing export.
  • Worth ~$25/month and, more importantly, it is the largest thing nobody understands.

Turn the capture off once Tuesday is in the bag

Enabled 2026-08-22 22:08 UTC · audit config under datastore.googleapis.com

Nothing disables this on its own. Baseline project ingestion is ~0.8 GiB/day against a 50 GiB/month free tier; Firestore data-access adds roughly 8–13 GiB/day. A few days is free to ~$10. Left running it is ~$100/month — more than Firestore reads themselves.

To disable

  • Drop auditConfigs from the project IAM policy and re-apply.
  • Delete sink firestore-data-access-to-bq or it keeps writing.
  • Dataset firestore_audit has a 14-day table expiry and cleans itself up.

Gotcha

  • The service name is datastore.googleapis.com. firestore.googleapis.com is rejected outright, even though the emitted logs carry it.

Checked and clear

Query latency is healthy

Excluding aggregations: p50 6.3ms, p95 16.2ms on 120,934 queries. Point reads p50 2.6ms.

Writes are clean

3,370 commits and 1,668 transactions on Monday, one rollback across two days. No write amplification, no hot-document contention.

No scanner recurrence

Monday's URL lookups look organic — 3,488 lookups across 979 distinct paths in the peak hour. The Aug 20 burst has not repeated.

Stage is idle

43 entries in the earlier stage capture, from a single editor session. Nothing runaway outside production.

How much to trust this

  • 41 hours, one weekday, and Monday is partial — the capture runs to 15:18 UTC, so Monday's totals are roughly two thirds of a full day. Percentages hold; absolute daily figures are floors.
  • Weekend and weekday differ by about 2× — 204k reads Sunday against 320k on a partial Monday. Anything derived from the earlier Sunday-only numbers understates the weekday shape, particularly for Links and Contents.
  • Items 01 and 02 are confirmed against source and deployed state. Item 05 is confirmed from operation metadata. Items 03, 04 and 06 are inferred from access patterns — confirm against the request handlers before sizing the work.
  • Earlier figures in this document have been corrected twice. The first pass rested on 82 minutes of late-night traffic; the second scaled shares against the full read bill before the export was identified. Per-issue dollar amounts have moved by roughly 8× as a result. The engineering findings have not changed — only the economics.
