Application reads are about 14% of the Firestore bill

Earlier versions of this document scaled per-collection shares against the full billed read volume. That was wrong by roughly 7×. Two independent sources — this audit capture and the firestore.googleapis.com/document/read_count metric — agree that application traffic is ~200–470k reads/day against ~2.1M billed. Caching every collection in the platform saves about $4/month. Do this work for latency and blast radius, not for the invoice.

Unbounded query Webapp ~half day

Notification settings fetch every subscription a user has, and the worst case is growing

Docer.DAL/Repositories/Notification/SubscriptionRepository.cs:23 — GetByUserId()

A bare WhereEqualTo("UserId", …) with no limit and no pagination, reached from GET /User/Subscriptions (UserController.cs:530) via NotificationBusiness.GetSubscriptions. Every load of that user's notification settings reads all of their subscriptions. 

largest single Subscriptions call, by day
  Sun Aug 23   2,079 documents
  Mon Aug 24   2,090 documents
  Tue Aug 25   2,839 documents   +36% in three days
  Wed Aug 26   2,839 documents

reads per call across the three weekdays
  Subscriptions       17.1   (peak 2,839 in a single call)
  Links                9.9
  Documents            1.2
  everything else      1.0

This is the finding that changed most over four days. The ceiling is not just absent, it is visibly rising — the worst call grew 36% during the capture window alone.

Fix

  • Paginate, or fetch only the subscription relevant to the entity being rendered.
  • GetByUserIdAndEntity() already exists two methods down and is the bounded form.

Why it matters

  • Cost is trivial — ~$0.11/month. The problem is it scales with one user's subscription count and has no ceiling.
  • Worst read amplification in the system by an order of magnitude.
03
Latency Editor-Frontend / Webapp ~1d

The Reference Links count tiles are the slowest thing in the database

features/reference-links-dashboard/index.tsx:116 — three separate count() calls per load

Every aggregation query in the capture was a count() against Links. They are 1.7% of calls and the worst latency in the system by a wide margin — 3.6× the median of an ordinary query and 12× at p95. The figures held steady across all three weekdays, so this is structural rather than a bad afternoon. 

Mon–Wed Aug 24–26 — latency by method
                        calls     p50      p95      p99    total
  RunAggregationQuery  14,923   24.3ms  205.9ms  267.4ms    812s
  RunQuery            401,911    6.8ms   17.4ms   55.5ms  3,616s
  BatchGetDocuments   470,993    2.7ms   10.1ms   15.2ms  1,715s

The code comment above these calls reads "Firestore's count aggregation is cheap and React Query dedupes on the same key." The dedupe works; the premise about cost does not. Three sequential 200ms calls put roughly half a second of latency in front of the dashboard before a row is drawn.

Fix

  • Collapse Total / Broken / Ignored into one pass, or denormalise the counters onto the document.
  • Document.NumberOfBrokenLinks already exists — the pattern is established.

Note

  • The filters are narrow (SourceTopicId, SourceDocumentId + IsValid), so this is latency, not billed reads.

Read amplification Webapp 1–3d

Two thirds of weekday reads are the same read repeated

Simulated TTL cache replayed over 490,563 reads from Tue–Wed Aug 25–26

Forty percent of it disappears with request-scoped memoisation alone — no shared cache, no invalidation, no staleness risk, just not fetching the same thing twice inside one request.

The heaviest individual repeats over those two days: Items by PublishUrl 46,806×, Accounts by Slug 44,795×, DocumentVersions by Id 27,249×, Contents by TopicVersionId 26,158×, one single Documents record 18,242×, and one single Accounts record 13,742×.

Start here

  • Request-scoped memoisation across the board — 40% for a fraction of the effort of a real cache.
  • Then a TTL cache on Accounts and Users, which reach 89% and 92%.

Not worth caching

  • Redirects — 21% hit rate. Nearly every lookup is a unique miss. Only negative caching helps, and only against scanners.
05
Cost Cloud-Functions ~half day

The daily backup is the largest identifiable line on the Firestore bill

Scheduler job firebase-schedule-firestoreBackup-us-central1 → ExportDocuments, 07:00 UTC daily

A full unfiltered export of every collection, every day. Firestore bills one read per document exported, so this is ~30M reads/month — roughly $18, against ~$6/month for all application traffic combined. It is three times the cost of everything the product does. 

export operation metadata, verified
  progressDocuments.completedWork   988,933
  progressBytes.completedWork       3,664,316,586   (3.66 GB)
  collectionIds                     (none — full database)
  runtime                           ~2m 45s
  backup bucket total               306 GiB

Options

  • Firestore managed backup schedules bill backup storage rather than read ops — likely cheaper and less code than the export-to-GCS function.
  • Or reduce cadence, or filter collectionIds to what a restore actually needs.

Check first

  • 306 GiB of retained backups with no visible lifecycle policy — worth confirming that GCS retention is intentional.
06
Read amplification Content-Processor ~1d

Link reconciliation reads ten documents per call and runs on every save

4,297 calls → 42,644 reads across the three weekdays — 4.1% of application reads

Links where SourceTopicId == … AND … pulls every existing link for a topic so the processor can diff against freshly extracted ones. That is a reasonable design, but at 9.9 reads per call it is the second-heaviest per-call read in the system, and one call returned 110 documents.

It also caches extremely well — 90% at a 60-second TTL, 94% at five minutes — which means the same topic is being reprocessed repeatedly in short windows. Worth understanding why before optimising the query itself.

07
Unexplained GCP investigate

Two fifths of the read bill still has no identified source

Tue Aug 25 — billed 2,148,507 · explained 1,281,543 · gap 866,964

Application reads and the daily export together account for ~60% of billed reads. The remaining ~870k/day is unaccounted for, and the ratio held on every complete day of the capture — so it is a standing feature of the bill, not a one-off. I would rather flag this than invent a cause.

Ruled out

  • Point-in-time recovery — disabled.
  • Managed backup schedules — none configured.
  • A second database — only (default) exists.
  • A second export job — one scheduler job, one daily operation.
  • count() aggregations — filters are narrow, so ~1 read each.
  • Incomplete capture — the Firestore metric independently corroborates the app figure within 10%.

Next step

  • Open a GCP support case with these three numbers; the SKU breakdown they can see is finer than the billing export.
  • Worth ~$25/month and, more importantly, it is the largest thing nobody understands.

The capture is far cheaper than predicted — leaving it on is a real option

Enabled 2026-08-22 22:08 UTC · audit config under datastore.googleapis.com

Earlier versions of this document estimated 8–13 GiB/day of log ingestion and warned of ~$100/month. Measured over four days, that was wrong by roughly an order of magnitude.

The error was in the volume estimate, not the price: I sized entry counts from billed reads (~2.1M/day) when application requests — the thing that actually generates log entries — are ~270–400k/day. Incremental cost of the capture is a few hundred MB a day, comfortably inside the free tier. Running it continuously would cost roughly nothing.

If you keep it

  • The BigQuery dataset has a 14-day table expiry, so it self-limits.
  • Re-check ingestion monthly in case traffic grows.

If you turn it off

  • Drop auditConfigs from the project IAM policy and re-apply.
  • Delete sink firestore-data-access-to-bq or it keeps writing.
  • Service name is datastore.googleapis.com; firestore.googleapis.com is rejected outright.

Checked and clear

Query latency is healthy

Excluding aggregations: p50 6.8ms, p95 17.4ms across 401,911 queries. Point reads p50 2.7ms.

Writes are clean

6,713 commits and 3,338 transactions over three weekdays, p95 75.8ms. No write amplification, no hot-document contention.

No scanner recurrence

Four days without a repeat of the Aug 20 burst. URL lookups track organic traffic.

Auth errors are noise

21 permission and authentication failures in 1,074,360 requests, all on Users and DraftTopicTrees. Nothing systematic.

How much to trust this

  • Four days, three of them weekdays — Aug 22 22:10 to Aug 26 18:36 UTC, 1,074,360 requests. Wednesday runs to 18:36 so its totals are slightly short of a full day; everything else is complete. This is the first version of this document with enough data to trust the shares.
  • Monday was atypical. 468k reads against ~280k on Tuesday and Wednesday, driven by heavy content editing. Percentages in item 04 come from Tue–Wed for that reason.
  • Items 01, 02 and 05 are confirmed against source, deployed state, or operation metadata. Items 03, 04 and 06 are inferred from access patterns — confirm against the request handlers before sizing the work.
  • Figures here have been corrected three times. The first pass rested on 82 minutes of late-night traffic; the second scaled shares against the full read bill before the daily export was identified; this one corrects a log-ingestion estimate that was ~10× too high. Per-issue dollar amounts have moved by roughly 8× across those revisions. The engineering findings have not changed once — only the economics attached to them.
